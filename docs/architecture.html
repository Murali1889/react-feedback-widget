How react-visual-feedback works

A top-to-bottom flow chart of what happens when a user clicks the feedback button.
Read the full integration guide → AI agent reference → README →
1

User triggers feedback

The reporter hits a keyboard shortcut or clicks a floating button.

  • Alt + A — open the form right now (manual feedback)
  • Alt + Q — pick an element first, then write feedback about it
  • Alt + W — record their screen + voice while reproducing the bug
2

The widget captures ALL the evidence

In the background, observers that have been running since page load assemble a full picture of the bug. The user doesn't have to type any of this — it's already there.

  • Screenshot of the clicked element (or full viewport)
  • What was clicked — React component name, source file:line, props + state
  • Reproduction recipe — last 30 clicks, inputs, route changes
  • Logs — recent network calls, console output, storage writes, errors
  • Performance — Web Vitals (LCP/CLS/INP), long tasks, memory, network speed
  • Environment — browser, viewport, color scheme, locale, timezone, build commit
💡 This is what makes the widget AI-friendly: the dev (or the LLM picking up the ticket) gets a complete repro without the user typing anything.
3

Compress the screenshot

A raw PNG screenshot is huge — typically 1 MB. We re-encode it to WebP at quality 0.85 in an off-main-thread Web Worker (using OffscreenCanvas).

  • Typical result: 1.0 MB → 20 KB (98% smaller)
  • No quality loss visible to a human
  • Main thread never blocks — the modal stays smooth
  • Compression starts the MOMENT the screenshot is captured, not at submit time. By the time the user finishes typing, it's already done.
⚡ Measured: cold submit takes 326 ms; warm submit (user typed for 2.5s) takes 53 ms. 6× faster because compression already finished while they were typing.
4

Build the AI-ready ticket

Everything from step 2 gets formatted into both Markdown (so a human can read it) and JSON (so a tool can parse it).

  • ## Summary — what the user wrote
  • ## Where — src/Checkout.jsx:42 with ±10 lines of code around it
  • ## Repro — the last 30 user actions, numbered
  • ## Logs — failing network calls, errors, recent storage writes
  • ## Environment — Vitals, browser, build commit, active flags
  • ## State at click time — the React component's props + state
🎯 An LLM that reads this can usually figure out the fix without ever opening the app.
5

Pick how to send the binary data

The screenshot (and any video) is binary. There are three ways to send it — the widget picks the best one based on your config and what's in the payload.

⤿ branches into one of three tiers ⤾
Tier 1

JSON

Inline the binary as base64 inside the JSON payload.

30.5 KB per request
When: no binary, or only local()
Tier 2 · default

multipart/form-data

Pull the binary into a separate part. No base64 overhead.

24.3 KB per request
When: any binary, no extra config — auto.
Tier 3 ★ best

Signed-URL direct upload

Browser PUTs the binary straight to S3 / R2 / Supabase Storage. Your app server never sees the bytes.

8.6 KB per request
When: upload.strategy: 'signed-url'
6

Dispatch to every destination — in parallel

Whichever strategy was picked, the final payload now goes out to every destination you configured. They all run at the same time; one failing never blocks another.

  • Each adapter resolves with { ok, id, url, durationMs }
  • The submission toast shows live per-destination status: ✓ local · ✓ github · ⚠ supabase failed
  • Failed-fanout toasts stay on screen 6 seconds (instead of 3) so the user has time to read

The security rule that runs through everything

No browser-side adapter ever holds a production credential.

  • Refused at build time — if you accidentally type a real token (ghp_…, lin_api_…, AKIA…, secret_…, Supabase service-role JWT, …) into a client adapter, it throws FeedbackCredentialLeakError before the app even runs.
  • Server-proxied by default — every server-proxied destination keeps its token in process.env. The browser POSTs to /api/feedback/<destination>; your server adds the token and forwards.
  • Public-token adapters are explicitly named *Public and ship with the exact RLS / lockdown SQL needed. Default is server-proxied; public is opt-in.
  • Signed-URL storage — the storage path is server-chosen from authContext.userId/projectId. A user with a valid session can ONLY write into their own scope. 5-minute URL expiry.
  • Hosted cloud uses Sentry-style write-only ingest tokens — identity, not auth. Worst case if leaked: garbage feedback. No data exfiltration possible.
